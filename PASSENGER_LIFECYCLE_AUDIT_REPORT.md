# Отчёт аудита жизненного цикла пассажиров (MetroParty)

Режим: **только аудит**, файлы проекта не изменялись. Визуальное/браузерное тестирование в среде выполнения не проводилось (анализ выполнен по коду и структуре проекта: `src/App.tsx`, `src/game/logic.ts`, `src/game/types.ts`, `src/styles.css`; других файлов, участвующих в жизненном цикле пассажиров, не выявлено).

## 1. Общий диагноз

### Почему пассажиры не начинают двигаться?
Пассажиры отображаются **не как свободно позиционируемые сущности на платформе**, а как обычные элементы потока (в строку/с переносом), при этом их логический старт движения дополнительно блокируется рассинхронизацией источников времени.

### Главная причина
**Конфликт CSS-позиционирования (элементы пассажиров не absolutely-positioned).**
- `src/App.tsx:540` — пассажир рендерится с классами `passenger-wrap dense free-passenger`.
- `src/styles.css:243–249` — `.free-passenger { position: absolute; left/top применяются; transform: translate(-50%,-50%); }`.
- `src/styles.css:253` — `.passenger-wrap { position: relative; display: inline-flex; flex-direction: column; align-items: center; }` объявлен **позже** при той же специфичности, поэтому переопределяет `position` на `relative`.

Итог: `left/top` из inline-стиля не задают абсолютные координаты в контейнере платформы, пассажиры участвуют в нормальном потоке/раскладке и выстраиваются **горизонтальными рядами с переносом на следующую строку**. Свободное перемещение по платформе по координатам при этом визуально невозможно.

### Дополнительные причины
1. **Несовместимость шкал времени для старта движения (критично для этапов ожидания/входа):**
   - `src/App.tsx:291,304,315` — `spawnMs/releaseMs` рассчитываются от `Date.now()` (`spawnMs + 300 + spawnOrder * 800`).
   - `src/App.tsx:362,395` — в цикле `requestAnimationFrame` используется `ts` (таймстемп RAF, сопоставимый с `performance.now()`), сравнение `if (ts < ps.releaseMs)`.
   - В браузере `Date.now()` (эпоха, ~10^12 мс) и `performance.now()/RAF ts` (время от старта страницы, ~10^3–10^6 мс) имеют разные начала отсчёта. Условие ожидания, как правило, остаётся истинным, из-за чего сущность не переходит из стадии `entering0` в `entering1` и логически не начинает маршрут.
2. **`spawnOrder` (глобальный счётчик появления) используется в формуле `releaseMs`** (`src/App.tsx:274,303,315`): индивидуальная задержка старта привязана к порядковому номеру появления (`spawnOrderRef`), а не вычисляется полностью независимо от накопленного порядка появления других сущностей (см. детали ниже). Это не объясняет «ряды», но создаёт нарастающую задержку старта у поздних пассажиров.

## 3. Найденные ошибки

### Ошибка 1 (главная, причина «рядов» и отсутствия свободного перемещения)
- **Файл:** `src/styles.css` (в связке с `src/App.tsx`)
- **Функция/участок:** правило `.passenger-wrap` переопределяет позиционирование `.free-passenger`
  - `src/App.tsx:533–545` — рендер: `<div ... className="passenger-wrap dense free-passenger ..." style={{ left: \`${pos.x}%\`, top: \`${pos.y}%\` }}>`
  - `src/styles.css:243–249` — `.free-passenger { position: absolute; ... left/top }`
  - `src/styles.css:253` — `.passenger-wrap { position: relative; display: inline-flex; ... }` (объявлено позже, перекрывает `position`)
- **Причина:** одинаковая специфичность селекторов, более позднее правило делает элемент относительно позиционированным.
- **Последствия:** пассажиры располагаются в нормальном потоке контейнера `.platform-rows` — **горизонтальными рядами с переносом**; абсолютные координаты движения не применяются, свободное перемещение по платформе не отображается.

### Ошибка 2 (блокировка логического старта/маршрута)
- **Файл:** `src/App.tsx`
- **Функция/участок:** `WaitingPassengers` — расчёт времени старта и проверка в `requestAnimationFrame`
  - `src/App.tsx:291` — `const nowMs = Date.now()`
  - `src/App.tsx:304` — `const spawnMs = nowMs`
  - `src/App.tsx:315` — `releaseMs: spawnMs + 300 + spawnOrder * 800`
  - `src/App.tsx:362` — `const step = (ts: number) => { ... }` (`ts` от `requestAnimationFrame`)
  - `src/App.tsx:394–406` — `if (ts < ps.releaseMs) { ... остаётся в (5,35), stage entering0 } else { ... stage = 'entering1' }`
- **Причина:** сравниваются значения из разных временных шкал (`RAF/performance.now` vs `Date.now`), из-за чего условие ожидания может не становиться ложным в реальном рантайме браузера.
- **Последствия:** пассажир не переходит из `entering0` в маршрут `entering1/entering2/waiting`, фактически не начинает движение по этапам (даже при корректной CSS-позиционировке).

### Ошибка 3 (накопление задержки старта по порядку появления)
- **Файл:** `src/App.tsx`
- **Функция/участок:** `WaitingPassengers`
  - `src/App.tsx:274` — `const spawnOrderRef = useRef(0)`
  - `src/App.tsx:296–318` — при первом появлении `id`: `const spawnOrder = spawnOrderRef.current++` и расчёт `releaseMs` с `spawnOrder * 800`
  - Формула присутствует и используется фактически: `spawnMs + 300 + spawnOrder * 800` (`App.tsx:315`)
- **Причина:** `spawnOrder` — глобальный монотонный счётчик появления, используемый для задержки; он не пересчитывается при удалении других, но определяет старт относительно накопленного числа появлений. У «поздних» пассажиров задержка растёт (`+800мс` на каждый предыдущий появившийся), что при большом количестве даёт длительное ожидание старта.
- **Последствия:** возможны чрезмерные/накопительные задержки старта у поздних пассажиров (особенно при 20), что воспринимается как «не начинают двигаться/очень долго стоят», даже если переход по времени технически сработает. Это расходится с требованием полностью индивидуального, не зависящего от количества других пассажиров времени старта.

### Дополнительные наблюдения (риски/несоответствия, не являющиеся первопричиной описанного симптома)
- **Инициализация в фазе рендера:** создание/удаление записей `posRef` выполняется прямо в теле компонента (`App.tsx:291–318`) — функционально работает с `ref`, но обновляет мутабельные структуры во время рендера.
- **Границы/область:** динамические границы рассчитываются от контейнера (`App.tsx:321–359`), но контейнер/родитель имеет `overflow: visible` и `clip-path` (`styles.css:210–211,236,239–240`), а нижняя граница — процент от контейнера, не от фактического положения депо; при ряде раскладок/ориентаций возможны визуальные выходы (требует визуальной проверки).
- **Посадка:** `autoFinalizeBoarding` завершает посадку логически по тикам без прохождения визуального пути до двери (`logic.ts:392–408`), что защищает от зависаний, но расходится с требованием «первый у двери при наличии места начинает посадку» как визуального этапа (поведенческое расхождение при сбоях UI-движения).

## 6. Итог

- **На каком этапе ломается цикл:** визуально — на этапе **отображения/позиционирования** (все сущности попадают в поток и выглядят рядами) — это проявляется сразу после появления. Логически — на этапе **ожидания старта** из-за несовместимости шкал времени (`Date.now()` vs `RAF/performance.now()`), что препятствует переходу `entering0 → entering1 → entering2 → waiting`; дополнительно старт зависит от глобального `spawnOrder`, создавая накопительную задержку.
- **Необходимые минимальные изменения:**
