PASSENGER_LIFECYCLE_FIX_01.md

MetroParty — восстановление движения пассажиров

Режим: точечное исправление подтверждённых ошибок.

1. Цель

Исправить три найденные ошибки:

1. Неправильное CSS-позиционирование пассажиров.
2. Несовместимость временных шкал "Date.now()" и "requestAnimationFrame".
3. Накопление задержки старта из-за глобального "spawnOrder".

Восстановить предусмотренный жизненный цикл пассажиров.

2. Обязательное сохранение

Не менять:

- игровые правила;
- семь этапов жизненного цикла;
- алгоритм генерации цветов и адаптации;
- правила подбора вагонов;
- вместимость вагонов;
- резервирование мест;
- очередь пассажиров к дверям;
- анимацию посадки;
- отправление поездов;
- уровни, таймер и паузу;
- визуальный стиль и композицию сцены.

Не переписывать "App.tsx" целиком.

Не менять "src/game/logic.ts" и "src/game/types.ts", если для исправления перечисленных ошибок это не требуется. Предпочтительно вообще их не трогать.

3. Исправление №1. CSS-позиционирование

Файл: "src/styles.css"

Проблема:
".free-passenger" задаёт "position: absolute", но более позднее правило ".passenger-wrap" задаёт "position: relative".

Необходимо:

- обеспечить "position: absolute" для пассажиров с классом "free-passenger";
- сохранить существующие "left", "top", "transform";
- сохранить размеры и оформление персонажей;
- не нарушить позиционирование облачков с репликами;
- убедиться, что координаты отсчитываются от правильного контейнера платформы;
- если контейнер не создаёт правильный контекст позиционирования, исправить это минимально.

Использовать селектор с достаточной специфичностью, например ".passenger-wrap.free-passenger".

Не менять позиционирование остальных элементов ".passenger-wrap".

4. Исправление №2. Единая шкала времени

Файл: "src/App.tsx", компонент "WaitingPassengers".

Найти создание "spawnMs", "releaseMs" и сравнение "releaseMs" с "ts" в цикле "requestAnimationFrame".

Сейчас:

- "spawnMs" создаётся через "Date.now()";
- "ts" приходит из "requestAnimationFrame";
- сравниваются значения с разными началами отсчёта.

Исправить так, чтобы все сравниваемые временные значения использовали одну монотонную шкалу времени.

Предпочтительный вариант:

- при создании пассажира использовать "performance.now()";
- для сравнения использовать "ts" из "requestAnimationFrame".

Проверить все места, где используются "spawnMs", "releaseMs" и "ts".

Не допустить повторного смешивания "Date.now()" и RAF timestamp.

Сохранить корректную работу паузы, продолжения и перезапуска. Не менять существующую механику игрового времени.

5. Исправление №3. Индивидуальная задержка старта

Файл: "src/App.tsx".

Сейчас используется:

"releaseMs = spawnMs + 300 + spawnOrder * 800"

Это приводит к накоплению задержки у поздних пассажиров.

Необходимо разделить:

Интервал появления

- пассажиры по-прежнему появляются последовательно;
- сохраняется существующий интервал между появлениями;
- появление следующего пассажира не зависит от движения предыдущего.

Индивидуальная задержка старта

- рассчитывается отдельно для каждого пассажира;
- определяется его собственным seed;
- не зависит от глобального "spawnOrder";
- не зависит от количества ранее появившихся пассажиров;
- не пересчитывается при удалении других пассажиров;
- остаётся неизменной на протяжении жизни конкретного пассажира.

Использовать небольшую задержку в диапазоне 300–1200 мс, детерминированно полученную из индивидуального seed.

Не использовать общий RNG для вычисления задержки.

Не удалять "spawnOrderRef", если он используется для других целей. Убрать только его влияние на индивидуальное время старта.

6. Проверка полного жизненного цикла

После исправлений проверить:

1. Пассажир появляется в координатах (5,35).
2. Остаётся там до своего индивидуального времени старта.
3. Проходит маршрут (5,35) → (7,35) → (30,80).
4. Переходит к свободному хаотичному блужданию.
5. При назначении движется к соответствующему вагону.
6. Корректно выстраивается в очередь у двери.
7. Садится при наличии свободного места.
8. При отмене назначения возвращается к свободному блужданию.
9. После удаления одного пассажира остальные продолжают двигаться.
10. Новые пассажиры не сбрасывают состояние существующих.

7. Проверка независимости

Проверить:

- 1 пассажир;
- 5 пассажиров;
- 20 пассажиров;
- появление новых пассажиров при уже движущихся существующих;
- удаление пассажира из середины массива;
- отмену назначения на вагон;
- отправление поезда;
- паузу и продолжение;
- рестарт.

Проверить, что время старта конкретного пассажира не меняется при добавлении или удалении других пассажиров.

8. Ограничения

Не добавлять:

- новые состояния пассажиров без необходимости;
- новую физику;
- столкновения и расталкивание;
- новые маршруты;
- фиксированные места на платформе;
- новые правила очереди;
- новые механики посадки.

Не проводить рефакторинг ради красоты кода.

Не менять алгоритм свободного блуждания, если он не является непосредственной причиной обнаруженной ошибки.

9. Сборка и отчёт

Выполнить:

- "npm run build";
- доступные проверки TypeScript;
- проверку отсутствия ошибок;
- проверку изменений через "git diff".

В отчёте указать:

1. Какие файлы изменены.
2. Какие именно ошибки исправлены.
3. Как теперь рассчитывается время старта.
4. Как обеспечено абсолютное позиционирование.
5. Какие проверки выполнены.
6. Результат сборки.
7. Какие проверки требуют реального запуска на Android.

Главный критерий: пассажиры должны снова появляться в точке (5,35), проходить входной маршрут и затем независимо хаотично блуждать по платформе. Все существующие игровые правила и механика посадки должны остаться прежними.
